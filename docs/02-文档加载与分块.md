# 02 文档加载与分块：RAG 效果的天花板在这里

对应代码：`ragdocs/loader/{discovery,parser,manifest}.py`

> 一个反直觉的事实：RAG 效果不好，十有八九不是模型不够强，
> 而是**喂给模型的片段本身就不对**。模型再好也没法从被切碎、
> 缺上下文的片段里还原出答案。这一层值得花最多的时间。

---

## 1. 三层职责要切开

| 模块 | 只负责 | 刻意不做 |
|---|---|---|
| `discovery.py` | 哪些文件进索引 | 不读文件内容 |
| `parser.py` | 读内容 → `Chunk` | 不碰向量框架 |
| `manifest.py` | 哪些文件变了 | 不解析文本 |

`parser.py` 产出的是纯 `dataclass`（`Chunk` / `DocMeta`），不是 llamaIndex 的
`TextNode`。所以这一层在**没装 llama-index、没起 Ollama** 的机器上也能完整跑。
我们就是靠这个，在模型还没拉下来时先验证了 2440 文件 / 2881 chunk 的正确性。

---

## 2. 用白名单，不用黑名单

`discovery.py` 用 `include_ext` 白名单（23 种纯文本扩展名）而不是「排除掉
不能读的」。原因：你的库里混着 `.git/`、17MB 的 `docs.db`、`.xlsx`、
老式二进制 `.doc`、`rclone.conf`（里面是凭据）……

白名单的语义是「**新增一种奇怪格式默认不进索引**」，比事后补救安全。
实测结果：

```
2440 待索引 / 35 跳过
跳过原因: 扩展名不在白名单 29、空文件 6
```

被跳过的 29 个正是 docx / doc / pdf / xlsx / 图片 / 无扩展名配置。
清单写到 `data/skipped_files.txt`，可审计。

另外 `dirnames[:] = [d for d in dirnames if d not in exclude_dirs]` 是
`os.walk` 的原地剪枝：改这个列表能让 walk **不再深入**那些目录，
比遍历完再过滤高效。

## 3. 你的笔记格式决定了专门适配

看三个真实样本：

```markdown
---
title: model
status: draft
updated: 2026-10-16
---

[[小模型]]

n-gram models
markov models    马尔科夫模型
recurrent neural networks   循环神经网络
```

三个特征，通用教程的 `SimpleDirectoryReader` 一个都不会处理：

### (a) YAML frontmatter 是白送的元数据
每篇都有 `title / status / updated`。`parser.py` 用正则切出头部，
`yaml.safe_load` 解析（解析失败退化成空字典，不让一篇坏笔记崩全库）。
再取一级目录名作 `topic`——你的 `0.x / 1.x / 2.x` 编号体系本身就是主题标签。

### (b) `[[双链]]` 要归一化
`[[小模型]]` → `小模型`。否则向量空间里「小模型」和「[[小模型]]」
是两个不同的词面，召回会漏。`[[目标|显示名]]` 统一取「目标」，
因为库内链接多用目标名作为概念词。

### (c) 短笔记绝不能硬切
`model.md` 正文才几十个字。若按 512 token 窗口切，一条完整概念会被劈开。
策略：`short_doc_threshold = 1200` 字符以内**整篇一个 chunk**。

**实测 2440 文件 → 2881 chunk，平均 1.18 chunk/文件**——绝大多数笔记
完整保留。这个数字是「策略生效」的证据，比看代码更有说服力。

## 4. 最重要的技巧：把元数据写进 embedding 文本

每个 chunk 长这样：

```
[path: 2.6-intelligence/NLP/transformer.md | title: transformer | topic: 2.6-intelligence | status: draft]
# transformer
transformer neural network
Some key elements of the model such as: ...
```

**为什么不用 `metadata` 字段就好？**
因为 `bge-m3` 这类 embedding 模型只对 `text` 编码。llamaIndex 的
`TextNode.metadata` 是给「过滤 / 展示」用的，不进向量。

于是当你问「**2.6-intelligence 里**关于 transformer 的笔记」时，
如果 `topic` 没进文本，纯向量检索几乎不可能命中「哪个目录」这个条件——
它只会找和「transformer」词面相近的东西，全库几十个目录里都可能有。

把路径 / 标题 / 主题写进 `text` 头部，是最省事、最有效的**元数据融合**。
`Chunk` 同时保留 `text`（带头部，用于 embedding）和 `raw_text`（干净原文，
用于展示），查询时给用户看的是后者。

> 进阶：metadata filtering（先按 topic 过滤再向量检索）、
> BM25 + 向量混合检索。本项目规模与「全部索引」的前提下用不上，
> 但知道这条路存在，将来效果不够时知道往哪走。

### llamaIndex 侧的对应细节
`_chunk_to_node()` 里两个参数值得注意：
- `excluded_embed_metadata_keys`：**不参与 embedding** 的 metadata；
- `excluded_llm_metadata_keys`：**生成时不塞进 prompt** 的 metadata。

`raw_text` 冗余存进 metadata，是为了查询时不必回读磁盘文件；
但要把它从生成 prompt 里排除，否则 LLM 会看到重复内容。

## 5. 长文怎么切：`_split_long`

按字符窗口（`chunk_size * 4` 近似 token，中英混排的经验换算），
带 `overlap` 保证跨窗语义连续。一个容易被忽略的细节：

```python
search_from = start + int(size * 0.75)
window = text[search_from:end]
cut = max(window.rfind("\n"), window.rfind("。"), window.rfind(". "))
if cut != -1:
    end = search_from + cut + 1
```

**不是正好在第 2048 个字符砍下去**，而是在窗口后 1/4 区间里找最后一个
换行 / 中文句号 / 英文句点收尾。避免把一行代码、一个词、半个句子劈开。
这种「软切点」对代码文件和中文长文都明显更友好。

## 6. 增量清单：为什么不能只看 mtime

`manifest.json` 记每个文件的 `size / mtime / sha1 / chunks`（旧版键名 `mtime_ns`，读时兼容）。

只用 mtime 的问题：`git checkout`、rclone 同步、touch 一下，
mtime 就变了，但内容一个字没改 → 白白重嵌 2900 个 chunk。

三元组判定逻辑（`compute_delta`）：
1. `size` 和 `mtime` 都没变 → 直接复用旧 sha1，连文件都不读；
2. 变了 → 才算一次 sha1：
   - sha1 相同 → 判为「未变」，只刷新 stamp（应对 git/rclone 场景）；
   - sha1 不同 → 进 `changed`，重新解析 + embedding；
3. 新路径 → `added`；清单里有、磁盘没了 → `removed`。

本地磁盘读一遍算 sha1 很便宜，embedding 才贵。**把计算花在便宜的地方
来省掉贵的地方**，这是增量索引的全部思路。

`save_manifest` 用「写 `.tmp` 再 `os.replace`」的原子替换，
避免中途被 kill 留下半截坏 JSON；`load_manifest` 遇到损坏清单会
退化成空清单（= 全量重建），不让服务起不来。

## 7. 一个真实发现的 bug：ref_doc_id

`_delete_by_paths` 最初是我按 node_id 前缀扫 `store.data.embedding_dict`
去删。查 `SimpleVectorStore.delete()` 源码才发现：

```python
def delete(self, ref_doc_id: str):
    for text_id, rid in self.data.text_id_to_ref_doc_id.items():
        if ref_doc_id == rid: ...
```

它按 **`ref_doc_id`** 删，而 `add()` 存的是 `node.ref_doc_id or "None"`。
我建的 `TextNode` 没设 `ref_doc_id` → 所有节点都是 `"None"` →
**一次都删不掉**，且直接操作 `store.data` 还是脆弱的私有 API 依赖。

修法：给每个节点设 `ref_doc_id = doc_id`（`doc_id = sha1(路径)[:16]`），
删除时 `store.delete(doc_id)` 一次清掉一个文件的所有 chunk。
走官方 API、按文件粒度、不碰内部结构。

> 教训：涉及「删 / 改」的逻辑，一定要读一眼依赖的源码确认语义，
> 不能凭方法名猜。这类 bug 不会在首次建索引时暴露，只会在你改了一篇
> 笔记之后悄悄留下脏数据。

---

## 小结：这一层你可以调的三个旋钮

`config/settings.yaml` 里：
- `chunking.short_doc_threshold` —— 调大 = 更多文档整篇保留；调小 = 切得更细
- `chunking.chunk_size` / `overlap` —— 长文粒度与上下文重叠
- `chunking.inject_fields` —— 想让检索更容易命中哪个维度，就加哪个字段

改完不用动代码，删 `data/` 重新 build 即可对照效果。
