# 01 环境与依赖：踩过的坑与背后的原理

对应代码：`requirements.txt`、`.venv/pip.conf`、`scripts/` 顶部的 `sys.path` 处理。

---

## 1. Python 3.14 很新，wheel 兼容性要先探

本机 `Python 3.14.8`。很多科学计算包（numpy、torch、chromadb）对刚发布的大版本
没有预编译 wheel，pip 会退化成「下载源码 → 本地编译」，轻则慢，重则因缺
编译器/头文件直接失败。

**动手前先查**，而不是装到一半再排错。用 PyPI 的 JSON API 看目标版本的
release 文件里有没有 `py3-none-any`（纯 Python，任何版本通吃）或 `cp314`：

```python
import urllib.request, json
d = json.load(urllib.request.urlopen(f"https://pypi.org/pypi/{pkg}/json"))
v = d["info"]["version"]
files = [f["filename"] for f in d["releases"][v]]
print([f for f in files if "cp314" in f or "py3-none-any" in f])
```

结果：
| 包 | 版本 | 3.14 兼容 |
|---|---|---|
| llama-index-core | 0.14.25 | `py3-none-any` ✅ |
| llama-index-embeddings-ollama | 0.10.0 | `py3-none-any` ✅ |
| llama-index-llms-ollama | 0.11.0 | `py3-none-any` ✅ |
| chromadb | 1.5.9 | 仅源码/需编译 ❌ |

**结论直接决定了架构**：放弃 chromadb，用 llamaIndex 内置的
`SimpleVectorStore`。减少一个需要编译的重依赖，也少一个服务进程。
这不是「凑合」，是因为全库才 ~2900 个 chunk，纯 Python 余弦相似度绰绰有余。

### 什么是 wheel / `py3-none-any`
wheel 文件名如 `foo-1.2.3-py3-none-any.whl`：
- `py3`：Python 3 任意小版本
- `none`：不依赖特定 ABI（没用 C 扩展）
- `any`：任意平台

带 `cp314-cp314-manylinux_x86_64` 的是针对 CPython 3.14 + Linux x86_64
编译好的二进制。带 C 扩展的包必须后者，纯 Python 包前者即可。

## 2. 没有 pip 怎么办：`ensurepip`

系统 `/usr/bin/python3` 没装 pip，但标准库自带 `ensurepip`：

```bash
python3 -m venv ~/Projects/rag/.venv
.venv/bin/python -m ensurepip --upgrade   # 得到 pip 26.2.1
```

不要在 Arch 上 `sudo pacman -S python-pip` 去污染系统环境，
venv 就是为这种隔离而生的。

## 3. 网络：pypi.org 通 ≠ 能下载

第一次装卡了 5 分 16 秒，一个包都没下完。诊断过程：

```bash
ps aux | grep pip          # 没有 gcc/cc1 → 不是编译卡住
curl -w "%{speed_download}" https://files.pythonhosted.org/   # 16 B/s !!
```

关键点：**`pypi.org/simple/`（索引页）能返回 200，但 wheel 实际存放在
`files.pythonhosted.org`**，两者是不同域名/不同链路。只测前者会误判「网络没问题」。

测了三个源：

| 源 | 速度 |
|---|---|
| `pypi.org/simple/` | 34 KB/s（还超时） |
| `files.pythonhosted.org` | 16 B/s ❌ |
| 清华 `pypi.tuna.tsinghua.edu.cn` | 198 KB/s ✅ |
| 阿里 `mirrors.aliyun.com` | 362 KB/s ✅ |

最终把镜像写进**项目内** `.venv/pip.conf`（venv 会优先读它），
不碰你的 `~/.config/pip/pip.conf`：

```ini
[global]
index-url = https://mirrors.aliyun.com/pypi/simple/
trusted-host = mirrors.aliyun.com
```

换源后 4 分 29 秒装完全部 70+ 个包，且全是预编译 wheel。

## 4. 版本不是写死的：mcp 装到了 2.3.0

`requirements.txt` 写的是 `mcp>=1.0.0`，实际解析到 **2.3.0**。
2.x 是一次 breaking change：

| | mcp 1.x | mcp 2.3（本机） |
|---|---|---|
| 高层 API | `FastMCP` | 改名 `MCPServer` |
| 注册工具 | `@server.list_tools()` + `@call_tool()` 两个分派函数 | `@server.tool()` 装饰普通函数 |
| schema | 手写 `inputSchema` JSON | 从类型注解 + docstring 自动生成 |
| 启动 | `stdio_server()` 异步上下文 | `server.run(transport="stdio")` |

我一开始按 1.x 教程写了 `list_tools/call_tool`，`import` 阶段就发现
`Server` 上根本没这两个属性。**没有将就着降级到 `mcp<2`**，而是改用 2.x
的 `MCPServer`——写法更简洁，且不用为了「和教程一致」去 pin 旧版。

> 教训：依赖写 `>=` 时，必须**实测装到的版本的真实 API**，不能凭记忆写。
> Python 生态里 0.x→1.x、1.x→2.x 的改名很常见。

顺带修掉的另一个真实 API 差异：
`OllamaEmbedding`（0.10.0）**没有** `request_timeout` 形参，超时要经
`client_kwargs={"timeout": ...}` 传给底层 `ollama.Client`；而
`Ollama`（LLM，0.11.0）直接支持 `request_timeout`。同一个厂商的两个集成包
参数不一致，只能看 `inspect.signature()` 确认。

> 注：上述 Ollama 集成现在**仅用于 `ask_docs` 的生成模型**（LLM）。embedding
> 默认已改用进程内 **llama.cpp（GGUF）**，不再经过 Ollama，故 Ollama 的
> timeout 细节主要服务于生成侧。`core/index.py` 的 `_build_service_context`
> 在 `embedding.backend=llamacpp` 时改用 `_LlamaCppEmbeddingAdapter` 注入
> 给检索侧，OllamaEmbedding 仅在 ollama 后端下使用。

## 5. 为什么脚本顶部要 `sys.path.insert`

`scripts/build_index.py` 用 `.venv/bin/python scripts/build_index.py` 直接跑时，
`sys.path[0]` 是 `scripts/`，不是项目根，`import ragdocs` 会失败。
三种解法：
- 装成包（`pip install -e .`）——本项目没做，避免多一个 pyproject；
- 用 `python -m scripts.build_index`——要求 scripts 是包；
- **脚本顶部插项目根**（本项目采用）：最简单，适合工具脚本。

MCP Server 用的是 `python -m ragdocs.mcp_server`，从项目根启动，不需要这行。

## 小结
这一阶段的三个可被复用的判断：
1. 装依赖前先查 wheel 兼容性，结果会反向决定架构选型；
2. 「索引站能访问」不代表「wheel 能下载」，要测真实文件域名；
3. 宽松版本约束装到的 API 可能与记忆不同，用 `inspect` 实测再写代码。
