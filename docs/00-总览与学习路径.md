# ragdocs：把个人知识库变成 agent 可调用的工具

> 目标：`~/Documents`（5704 个文件、2208 篇 Markdown 笔记）→ RAG 服务 → 通过 MCP 暴露给 agent。
> 技术栈：llamaIndex 0.14 + MCP 2.3（stdio）。embedding 默认走本地
> `sentence-transformers`（CPU 即可、稳定）；Ollama 可选（见 docs/06 第 7 节，
> 本机 bge-m3 worker 不稳定）。`ask_docs` 的 LLM 仍可用本地 Ollama（可选）。
> 全程离线，文档不出本机。

---

## 一、先建立整体心智模型

RAG 不是「一个大模型读你的文档」，而是**两段式**：

```
【离线：建索引】                       【在线：查询】
文件 → 解析/分块 → 向量化 → 存盘        问题 → 向量化 → 找相似片段 → (可选)交给 LLM 生成
   (embedding 模型)  (向量库)              (同一个 embedding 模型!)   (LLM)
```

最容易忽略的一点：**建索引和查询必须用同一个 embedding 模型**。
向量是「模型对文本的坐标」，换模型等于换坐标系，旧向量全部作废。
这也是为什么 `manifest` 里虽然没存模型名，但换 `embed_model` 后必须全量重建
（本项目目前靠你手动删 `data/` 重建，见「已知限制」）。

### llamaIndex 在本项目里的组件对照表

| 本项目概念 | llamaIndex 对象 | 作用 |
|---|---|---|
| `Chunk` | `TextNode` | 最小检索单元，带 metadata |
| `remote`（默认）：讯飞 MaaS `Qwen3-Embedding-8B` | OpenAI `/embeddings` 协议 | 文本 → 向量（768 维，云端，本机无 GPU 时首选） |
| `llamacpp`（可选） | llama.cpp 读本地 GGUF `bge-m3` | 文本 → 向量（1024 维，进程内，需 GPU/CPU 推理） |
| Ollama `bge-m3`（可选） | 直调 `/api/embed` | 文本 → 向量（1024 维，本机实测 worker 易卡死） |
| 本地 JSON | `SimpleVectorStore` | 向量表，可 persist / 载入 |
| 存储上下文 | `StorageContext` | 管 vector store / docstore |
| 索引门面 | `VectorStoreIndex` | 提供 retriever / query |
| Ollama `qwen2.5` | `Ollama` (LLM) | `ask` 时做带上下文生成 |
| `RagIndex` | 本项目自己写的门面 | 隔离框架，统一 build/load/search/ask |

看代码时按这张表对照 `ragdocs/core/index.py`，比从上往下读快得多。

## 二、为什么要分这么多层

```
ragdocs/
├── config.py            # 所有可调参数集中到 settings.yaml
├── loader/
│   ├── discovery.py     # 决定「哪些文件进索引」（不读内容）
│   ├── parser.py        # 读内容、解析 frontmatter、分块 → Chunk
│   └── manifest.py      # 增量清单，避免全量重嵌
├── core/
│   └── index.py         # 唯一依赖 llamaIndex 的地方
└── mcp_server.py        # 唯一依赖 MCP SDK 的地方
```

划层的实际收益（不是为架构而架构）：
1. **加载层不依赖向量框架**：`discovery/parser/manifest` 只用标准库 + pyyaml。
   本机在 Ollama 没起、模型没拉时，我们照样跑通了 2440 个文件的发现与
   2881 个 chunk 的解析验证——就是因为这层是干净的。
2. **换框架只改一个文件**：将来想试 LangChain 或自研，只动 `core/index.py`。
3. **换协议只改一个文件**：想加 HTTP API，不用碰索引逻辑。

## 三、本项目的关键设计决策（以及为什么）

### 1. 不用 chromadb，用内置 SimpleVectorStore
`chromadb` 在 Python 3.14 上需要现场编译，且会引入一大堆依赖。
全库只有 ~2900 个 chunk，纯 Python 的余弦相似度完全够。
代价：暴力检索 O(n)，十万级以后才需要换 Qdrant/Milvus——那时只改
`StorageContext` 一行。

### 2. 短文档整篇不切
你的笔记里大量是十几行的概念卡（`model.md` 才 10 行）。
硬按 512 token 切会把一条完整概念劈成两半，检索时两边都残缺。
策略：`short_doc_threshold=1200` 字符以内整篇一个 chunk，长文才滑窗切。
实测 2440 文件 → 2881 chunk，平均 1.18，**绝大多数没被切碎**。

### 3. 把元数据「写进 embedding 文本」
每个 chunk 头部注入 `[path: ... | title: ... | topic: ... | status: ...]`。
原因：`bge-m3` 只对 `text` 编码，metadata 字段不参与相似度。
你问「2.6-intelligence 里关于 transformer 的笔记」时，若 `topic` 没进文本，
纯向量几乎命中不了「哪个目录」这个条件。写进文本是最省事的元数据融合。
（进阶做法是 metadata filtering + hybrid search，本项目规模用不上。）

### 4. `[[双链]]` 归一化
Obsidian 风格的 `[[小模型]]` 去掉方括号保留「小模型」，
否则「小模型」和「[[小模型]]」在向量空间里是两回事，召回会漏。

### 5. 增量索引用三元组判变
`size + mtime_ns + sha1(内容)`。只看 mtime 会被 `git checkout` / rclone
同步误判「文件变了」从而白白重嵌；加内容 hash 后内容没变就不重算。

### 6. MCP 用 stdio 而非 HTTP
不开端口、不鉴权（进程边界即信任边界）、随 agent 启停。
**头号坑**：stdout 是 JSON-RPC 专用通道，日志必须走 stderr，打一行 print
到 stdout 就会让协议解析失败。`mcp_server.py` 里的 `_log()` 就是为此。

### 7. 依赖走国内镜像
`files.pythonhosted.org` 在本机只有 ~16 B/s，pip 卡了 5 分钟一个包没下完。
改成阿里源（360 KB/s）后 4 分钟装完全部。镜像写在**项目内**
`.venv/pip.conf`，不污染你的全局配置。

## 五、与库内已有 `docindex` 工具的关系（重要）

开发过程中发现 `~/Documents/0.0-how-docs/tools/docindex/` 已经有一个
自研索引器：SQLite + FTS5 trigram 全文索引、frontmatter/tags/标题/双链
结构化查询、**自带 MCP stdio server**、还有 Web 界面，并明确「文件是唯一真源、
DB 是可重建派生缓存」。

**这不是重复造轮子，是互补的两层检索**：

| | docindex（已有） | ragdocs（本项目） |
|---|---|---|
| 检索 | 词法 / 精确：FTS5 trigram、SQL 过滤 | 语义 / 模糊：向量相似度 |
| 擅长 | `status=draft`、某个词在哪、反链、失效链接 | 用词不同但意思相近、概念性提问 |
| 元数据 | 结构化、可查询、可 `edit` 写回 frontmatter | 注入 embedding 文本，不做结构化查询 |
| 成本 | 纯标准库，秒级重建 | 需 embedding，首次较慢 |
| 依赖 | 无 | llamaIndex + Ollama |

举例：「哪篇笔记提到 n-gram」→ docindex 更快更准；
「我关于『记忆如何形成』都记了什么」→ ragdocs 才能召回不同措辞的段落。
两者的 MCP server 名不同（`docindex` / `ragdocs`），**可同时挂到同一个 agent**。

> 一个值得后续做的方向：让 `ragdocs` 的 `discovery` 直接复用 docindex 的
> `documents` 表（已有 sha1/mtime/title/status），省掉自己维护 manifest，
> 并天然获得 tags 过滤能力。当前刻意保持独立，是为了让本项目自成闭环、
> 便于学习；等跑顺了再考虑合并派生层。

已知限制（刻意留白，不提前过度设计）：
- **换 embedding 模型不会自动重建**：需手动删 `data/` 后重新 build。
- **docx/pdf/xlsx 未索引**：第一阶段只做纯文本，跳过的文件记在
  `data/skipped_files.txt`。老 `.doc` 是二进制格式，解析不可靠。
- **`ask_docs` 是「拼上下文 + 一次 LLM」**：不是 llamaIndex 的 query_engine，
  刻意保留最直白的形式，方便你先看懂 RAG 的最小闭环。
- **单进程、无并发控制**：多个 agent 同时 `reindex_docs` 会打架；单人使用够。
