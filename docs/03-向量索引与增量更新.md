# 03 向量索引与增量更新

对应代码：`ragdocs/core/index.py`

---

## 1. 一个必须记住的公理：坐标系要一致

```
建索引:  chunk.text --[embedding 后端]--> v1 ┐
                                           ├─ 余弦相似度才有意义
查询:    "问题"    --[同一个后端]----> q  ┘
```
（当前默认后端见 `config/settings.yaml` 的 `embedding.backend`：本机无 GPU，
默认 `remote` = 讯飞 MaaS `Qwen3-Embedding-8B`，**768 维**；可选 `llamacpp`
本地 `bge-m3` GGUF 为 1024 维。换后端必须删 `data/` 重建，维度不同会冲突。）

embedding 模型定义了「把文本映射到哪个向量空间」。
**换模型 = 换坐标系**，旧向量和新向量之间算相似度毫无意义。

所以：
- 建索引和查询必须用同一个 `embed_model`（代码里由 `_build_service_context`
  统一注入 llamaIndex 的全局 `Settings.embed_model`，两处自然一致）；
- 配置里改了 `embed_model`，必须删 `data/` 全量重建。
  本项目 `manifest.json` 目前**没记模型名**，不会自动检测——这是刻意留的
  已知限制，见文末。

## 2. 延迟导入：让重依赖只在该出现的地方出现

`index.py` 里所有 `from llama_index...` 都写在**函数体内部**，模块顶层只有
标准库 + 本项目自己那几层。

好处在本次开发中立刻兑现了：模型还没 pull、Ollama 还没模型时，
我们照样能 `import ragdocs.core.index`、能跑 `discovery/parser` 的全库验证、
能起 MCP server 调 `rag_stats`。如果顶层就 import llamaIndex，任何配置或
环境问题都会让整个包起不来，排查范围一下子变大。

> 这不是性能优化，是**依赖边界**。原则：一个模块只 import 它这一层真正
> 需要的东西；框架依赖集中在 `core/` 和 `mcp_server.py` 两处。

## 3. `_build_service_context`：llamaIndex 0.14 的全局注入

```python
from llama_index.core import Settings as LISettings
LISettings.embed_model = OllamaEmbedding(...)
LISettings.llm = Ollama(...)
```

老教程里到处传 `service_context=ServiceContext.from_defaults(...)`，
0.14 起推荐用全局 `Settings`。全局注入对本项目特别合适：只有一个索引、

> **当前实现的偏差（重要）**：本项目 2026-11 修订后，**不再让 llamaIndex 在
> build 时 embed 节点**（逐条太慢，见 docs/06 第 7 节），而是 `_batch_embed`
> 自己批量产出向量填进 `node.embedding`，因此 `Settings.embed_model` 主要
> 供 `ask_docs` 的 LLM 侧使用；检索时的 query 向量也由 `_batch_embed`
> 统一产出，保证 build 与 query **用的是同一个模型/后端**，坐标系一致。
> 切换 `embedding.backend`（ollama ⇄ local）只需改配置、删 `data/` 重建。
只有一组模型，不需要多套上下文并存。

注意两个包的参数不一致（靠 `inspect.signature` 查出来的）：

| 包 | 超时参数 |
|---|---|
| `OllamaEmbedding` 0.10.0 | 无此形参，须 `client_kwargs={"timeout": ...}` |
| `Ollama` (LLM) 0.11.0 | 直接 `request_timeout=...` |

## 4. SimpleVectorStore 的真实结构

不用 chromadb，落盘后 `data/index/` 里是一堆 JSON。结构（读源码确认）：

```
SimpleVectorStore.data: SimpleVectorStoreData
  ├── embedding_dict        { node_id: [float, ...] }     ← 向量
  ├── text_id_to_ref_doc_id { node_id: ref_doc_id }       ← 删除用的索引
  └── metadata_dict         { node_id: {...} }            ← 元数据
```

`metadata_dict` 与 `docstore.json` 里每个节点的 metadata 含 `doc_id / path /
title / topic / status / updated / ext / ordinal / raw_text`，以及内部字段
`ino`（inode 号，见第 5 节 (d)，不进 embedding 文本）。
`manifest.json` 每条记录另有 `size / mtime_ns / sha1 / chunks / ino`。
（本机 docs_root 单分区，`st_dev` 恒为常量、冗余，故只存 `ino`。）

`StorageContext.persist(dir)` 把它写盘，`from_persist_dir` + 
`load_index_from_storage` 读回来。**载入时不调用 embedding**，
所以 MCP server 启动很快——这也意味着 agent 第一次调 `search_docs`
之前不需要等任何初始化。

### 检索就是一次暴力余弦

`index.as_retriever(similarity_top_k=k).retrieve(query)` 会把 query 编码后
和 `embedding_dict` 里全部向量算相似度，取 top-k。2900 条向量纯 Python
几毫秒级。**什么时候该换专用向量库？** 当 chunk 到十万级、或需要
metadata 过滤 / 分布式时。换的时候只改 `StorageContext` 的构造一行，
`RagIndex` 的其余代码不用动——这就是第 2 步划层的回报。

## 5. 增量更新的完整流程（`RagIndex.build`）

```
discover()                      → 2450 个候选文件
compute_delta()                 → added / changed / removed / unchanged / moved
对 added+changed 调 parse_file  → 新 Chunk → _chunk_to_node → 新 TextNode
   ↓
已有索引?
  否 → VectorStoreIndex(new_nodes, StorageContext(SimpleVectorStore()))
  是 → _delete_by_paths(removed ∪ changed)   ← 先删旧（moved 已从中剔除）
       self._index.insert_nodes(new_nodes)     ← 再插新
       _relabel_moved(moved)                  ← 只重贴元数据，不重 embed
   ↓
persist() → data/index/*.json
commit_manifest() → data/manifest.json（以新路径为 key 写回）
```

两个容易出错的点：

**(a) 「修改」要先删后插，不能只 insert。**
`insert_nodes` 按 node_id 新增；同路径重新解析出的 `chunk_id` 虽然稳定
（`doc_id:ordinal`），但若一篇文档从 3 个 chunk 变成 2 个，第 3 个旧节点
会残留成脏数据。所以 `changed` 必须整篇先删再插。

**(b) 删除粒度是「文件」不是「chunk」。**
靠 `ref_doc_id = doc_id`（见 02 文档第 7 节）：`store.delete(doc_id)`
一次清掉该文件所有 chunk。

**(c) 空库保护。**
若 `new_nodes` 为空且索引不存在，仍要建一个空 `VectorStoreIndex([])`，
否则后续 `insert_nodes` 没有载体。

**(d) 改名/移动（mv）识别：路径变了但内容没变，不该重 embed。**
manifest 以**相对路径**为主键，所以单纯 `mv a.md b.md` 会被朴素地判成
`removed=[a.md] + added=[b.md]`，进而触发「删旧向量 + 重新调云端 embedding」——
内容一个字没改却要重算，既慢又可能撞限流。

`compute_delta()` 末尾的 `_detect_moves()` 做两趟结构变更还原——
**inode 号是「优先 hint」，sha1 是「正确性兜底」**：

1. **inode 精确配对**：同文件系统内 `mv` 保留 inode 号（`st_ino`）。`removed` 侧取
   清单里存的上次 `ino`，`added` 侧取当前 `stat().st_ino`；同 `ino` 排序后 zip
   一对一命中。比算内容 sha1 更快，且能区分「内容相同但确实是不同文件」。
2. **sha1+size 回退**：对第一趟未消费的 `removed`/`added`，沿用 `(内容 sha1, size)`
   排序 zip 一对一配对。

> **inode 的可靠边界（关键）**：inode 号是「本机、本文件系统、此刻」的瞬时属性。
> 跨文件系统 mv、git checkout、rclone/网盘同步、编辑器「写临时文件 + rename 覆盖」、
> 换机，都会让它变化或被复用。所以它**只做本机快速配对 hint，失配一律忽略并回退
> sha1，绝不因 inode 不同而拆散一对 sha1 相同的 mv**，也不作为长期主键。
>
> **为什么只存 `ino` 不存 `dev`**：POSIX 里唯一标识一个文件本应是 `(st_dev, st_ino)`
> ——`ino` 只在单个文件系统内唯一，`dev` 标识它属于哪块设备。但本项目 `~/Documents`
> 整个挂在同一个 ext4 分区、无子挂载点，`st_dev` 实测恒为常量、不携带区分信息，
> 属冗余字段，故剪除，只用 `ino`。代价是若将来 docs_root 混入第二个文件系统，
> 极低概率的 `ino` 撞号可能导致误配——真到那一步再加回 `dev` 即可。

配上的 `(旧路径, 新路径)` 进入 `Delta.moved`，并从 `added` / `removed` 中剔除：
于是 `to_process`（= added+changed）不含它们 → **不 parse、不 embed、零远程调用**；
`delta.removed` 不含旧路径 → `_delete_by_paths` 不会误删要保留的向量。
`stamps[新路径]` 被改写成「复用旧 sha1/chunks、取新路径当前 stat（含 ino）」的
stamp，`commit_manifest` 即以新路径为 key 写回，`total_chunks` 不丢失。
`RagIndex._relabel_moved()` 随后把索引里 `metadata.path == 旧路径` 的节点就地改成
新路径（同步 `topic` / `title` / `ino`），`docstore.add_documents(allow_update=True)`
覆盖；`vector_store.data.metadata_dict` 里的冗余副本也一并同步。

**`ino` 落在三处**（都不是主键）：
- `manifest.json` 每条记录：`"ino"`，供下次本机配对与审计。旧记录缺字段时
  按 0 处理，向后兼容、**不升 version**。
- 每个 `TextNode` 的 `metadata.ino`（`DocMeta` → `_chunk_to_node`），
  并列入 `excluded_embed_metadata_keys` / `excluded_llm_metadata_keys`，确保不进
  embedding 文本或 LLM 上下文。`_make_header` 的白名单同样不含它。
- `compute_delta` 的 `FileStamp`。

`Hit` 刻意**不暴露** inode：它是内部易失标识，不该泄漏给 agent / CLI。

manifest 结构（version 1）与 `doc_id` 生成规则**完全不变**，所以这是一次**兼容迁移**：
旧 manifest 无需转换，下次 build 自动按新逻辑判定，不删 `data/`、不重建索引。

**代价（刻意接受，不掩盖）：**
`_make_header` 把 `path/topic/title` 写进了 embedding 文本（`chunk.text`）。mv 后
只更新 `metadata`，**不动 `text`、不动向量、不动 `doc_id`/`chunk_id`**——
所以 `Hit.path` 显示新路径、纯内容检索完全正常，但用「新目录名/新标题」做语义搜索时，
向量里内嵌的仍是旧字段，会滞后；`doc_id` 也冻结为旧路径的哈希。要让这两者完全一致，
只能走「内容变更」路径重 embed（此时本来就该重算）。真正要彻底刷新，删 `data/` 全量
重建即可，但那是一笔云端调用成本，日常改名不值得。

> 注：真正「删除旧文件 + 新增同内容新文件」也会被判为 mv（内容指纹相同无法区分），
> 这无害——结果只是省了一次 embed、把向量留用并改了路径标签。

## 6. `search` 与 `ask` 的区别（给 agent 用的两个工具）

| | `search_docs` | `ask_docs` |
|---|---|---|
| 做什么 | 只向量检索，返回原文片段 + 路径 | 检索 + LLM 生成答案 |
| 调 LLM | ❌ | ✅ |
| 适用 | 找原文、找概念定义、agent 自己要用片段 | 需要综合多篇笔记的自然语言回答 |
| 返回 | `count` + `hits[]`（含 `text`） | `answer` + `sources[]` |

**`ask_docs` 刻意没用 llamaIndex 的 `query_engine`**，而是最直白的三步：

```python
hits = self.search(question)                  # 1. 检索
context = "\n\n".join(片段 + 来源标注)         # 2. 拼上下文
prompt = system_prompt + context + question   # 3. 一次 llm.complete()
```

理由：这是 RAG 的**最小闭环**，一眼能看懂「检索到的东西是怎么进 prompt 的」。
`query_engine` 内部会做 response synthesis、refine、tree-summarize 等，
对学习阶段反而是黑盒。等你需要多轮综合 / 引用对齐时再换不迟。

`system_prompt` 里明确写了「只依据片段回答、不要编造、结尾列引用路径、
片段不足就明说」——这是抑制幻觉最便宜也最有效的一层。

## 7. `Hit` 是给外部看的，不是 llamaIndex 对象

`search()` 返回 `list[Hit]`（纯 dataclass），MCP 层再序列化成 dict。
好处：agent / CLI / 未来的 HTTP 接口拿到的是稳定结构，
llamaIndex 哪天升级改了 `NodeWithScore` 也不会波及协议层。

`score` 为 `None` 是允许的（某些 retriever 不返回分数），
`_hit_dict` 里做了 `round(x, 4) if x is not None` 的保护。
`threshold` 默认 0（不过滤），设 0.3~0.5 可降噪——但要先看实际分数分布
再定，别拍脑袋。

## 8. 已知限制（刻意不提前解决）

1. **换 embed_model 不自动重建**：manifest 没存模型名。改配置后手动删 `data/`。
   加一个 `meta.json` 记录模型名并在 `load()` 时校验，是十行代码的事，
   等真的换模型时再加。
2. **无并发控制**：两个 agent 同时 `reindex_docs` 会同时写 manifest / index。
   单人使用够；多人场景需加锁。
3. **`_persist` 里重复跑了一次 `discover()`**：只为写跳过清单，多一次目录遍历。
   可以缓存，但 2440 文件的 walk 不到 0.1 秒，不值得为此加状态。
4. **`ask_docs` 无对话历史**：每次独立问答。要做多轮得在 MCP 层维护 session。

> 这四条都是「知道存在、判断当前不需要、留好扩展位置」，
> 而不是遗漏。写清楚限制比假装系统完备更有用。
