## 4. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `pip install` 卡住不动 | `files.pythonhosted.org` 慢。确认用了 `.venv/pip.conf`（阿里源），见 docs/01 |
| `ModuleNotFoundError: mcp.server.fastmcp` | 装的是 mcp 2.x，类名是 `MCPServer`。本项目已按 2.x 写 |
| MCP 连不上 / 握手超时 | 99% 是往 **stdout** 打了东西。检查所有 `print`，日志必须 `file=sys.stderr` |
| `FileNotFoundError: 索引尚不存在` | 先跑 `scripts/build_index.py`，或让 agent 调 `reindex_docs` |
| embedding 报 `FileNotFoundError: llama.cpp 嵌入模型不存在` | `llamacpp_embed.model_path` 指向的 GGUF 没下载，按第 7 节下载 bge-m3 GGUF |
| 显存 OOM（7b） | 配置里 `llm_model` 改 `qwen2.5:3b`，重跑即可（不影响已建索引） |
| 换了 `embed_model` 后检索全乱 | 坐标系变了。删 `data/` 全量重建（当前不自动检测，见 docs/03） |
| 改了笔记但检索还是旧内容 | 调 `reindex_docs` 或重跑 `build_index.py`；确认 manifest 里该文件进了 `changed` |
| 改名/移动文件后 `build` 报「移动 N」 | 正常：`compute_delta` 先按 inode 号 `ino` 本机快速配对、失配回退 `sha1+size`，把 `removed+added` 还原成 mv，**不重 embed、零远程调用**，只就地更新路径元数据。跨机/同步后 inode 会失效，自动回退 sha1 仍正确。本机单分区、dev 恒为常量故不存。构建统计里 `moved` 即其次数（见 docs/03 第 5 节 (d)） |
| 某文件搜不到 | 查 `data/skipped_files.txt`：多半是扩展名不在白名单 / 空文件 / 正文为空 |
| `yaml.parser.ParserError` | YAML 列表要一行一个 `- 值`，不能 `- "a" "b" "c"`（本次踩过两次） |
| 想排除个人资料 | `privacy.exclude_enabled: true` + reindex，见 docs/05 |

## 7. embedding 后端与本地推理在本机的现实（已确诊）

本项目 `config/settings.yaml` 的 `embedding.backend` 支持四种：

| backend | 实现 | 本机状态 |
|---|---|---|
| `remote` | 远程 embedding 服务（OpenAI `/embeddings` 协议，如讯飞 MaaS `Qwen3-Embedding-8B`，768 维） | **默认**。本机无可用 GPU 时最省事，文本出网 |
| `llamacpp` | 进程内 llama.cpp 读本地 GGUF（bge-m3，1024 维），无服务依赖 | 可用，但本机纯 CPU 慢；独显不可用 |
| `ollama` | 调 Ollama `/api/embed` | 本机实测 bge-m3 worker **会卡死**，见下 |
| `local` | 进程内 `sentence-transformers` 跑 `BAAI/bge-m3` | 需另装 `torch sentence-transformers`（当前未装） |

**维度不统一**：`remote` 默认 768 维，`llamacpp`/`ollama`/`local` 的 bge-m3 是
1024 维。**换后端后必须删 `data/` 全量重建**，否则新旧向量维度不同会导致检索
报错或返回垃圾结果。

### 本机 GPU 不可用的真相

本机有 RTX 4050 独显，但**风扇有物理隐患**：高负载下会触发整卡复位
（`dmesg` 见 `NV_ERR_GPU_IN_FULLCHIP_RESET`），且崩溃时风扇仍在狂转——不是
过热，是供电/散热链路不稳。因此：

- `llamacpp` 的 `n_gpu_layers` 设为 `0`（纯 CPU），**不把模型卸载到独显**；
  试过 `-1` 全卸载，直接把卡干崩。
- 所以本地 embedding 实际只能跑 CPU，慢；最终选 `remote` 把 embedding 外包给
  云端 MaaS，绕开硬件问题。

### remote 后端要点

- 配置段 `remote_embed`：`base_url`（含 `/embeddings` 的完整地址）、
  `api_key`、`model`、`timeout`、`dims`（0=用服务端默认，实测 768）、
  `batch_size`（单次请求文本条数，**默认 8**）。
- 批量调用：接口支持 `input` 传数组，代码按 `batch_size` 切块一次多文本，
  减少往返（`_embed_remote`）；检索侧的 query 向量化走同协议的
  `_RemoteEmbeddingAdapter`，`search_docs` 不依赖 Ollama。
- `api_key` 是敏感凭证，**勿 `git commit`**。参照 `~/Projects/agent` 的密钥管理：
  `config/settings.yaml` 里 `api_key` 只留空占位，真实值放被 `.gitignore` 忽略的
  `user/secrets.yaml`（键路径同为 `remote_embed.api_key`），或用环境变量
  `XF_YUN_API_KEY` 注入。优先级：`user/secrets.yaml` > 环境变量 > 占位。
  聊天里贴过的 key 建议去控制台 revoke 重建。

### remote 批量超时踩坑（已确诊）

**现象**：`build --limit 20` 偶尔 `TimeoutError: The read operation timed out`
（ssl 读超时，60s 内服务端未返回）。

**排查**：用 curl 直测讯飞批量能力——20 条中等长度 1.2s、50 条短文本 1.5s，
**服务本身秒回**，排除网络/模型限速。进一步统计前 20 个文件实际解出
**179 个 chunk、共 35.8 万字符（平均单 chunk 2003 字）**。

**真凶**：旧代码 `batch_size` 默认 **64** 且 `_batch_embed` 默认 64 被直接传给
remote，于是把 64 个 ~2000 字的长文本（约 12.8 万字）**一次性拼成单个 POST**
发给讯飞，单请求体过大、服务端处理超 60s 触发读超时。

**修复**：
- `RemoteEmbedCfg` 新增 `batch_size`（默认 8），`_batch_embed` 在 remote 分支
  改用 `cfg.remote_embed.batch_size` 而非全局默认 64；
- `remote_embed.timeout` 由 60 调到 **120**；
- 实测 179 chunk ÷ 8 ≈ 23 次小请求，每次 1~2s，构建稳定通过。

**经验**：云端 embedding 服务的单请求体宜小（batch_size 8~16），不要把长文本
大批量塞进一个请求；长文本优先靠分块（chunk）控制单条长度，而非靠大 batch。

### llama.cpp 后端要点（备选）

- **GGUF 模型需自行准备**：Ollama 的 `bge-m3` 不是裸 GGUF，不能复用。
  从 ModelScope 下现成的，例如 `gpustack/bge-m3-GGUF` 的 `bge-m3-Q8_0.gguf`
  （约 606MB），放到 `llamacpp_embed.model_path`（默认 `~/models/bge-m3-q8_0.gguf`）。
  （注：HuggingFace 直连在本机极慢，优先用国内镜像。）
- **Python 3.14 无预编译 wheel**：`llama-cpp-python` 会源码编译，需本机
  有 `gcc` 与 BLAS（OpenBLAS）。如需 GPU 后端还要装 `cuda` 开发包并用
  `CMAKE_ARGS="-DGGML_CUDA=ON ..."` 编译（本机因独显隐患未走 GPU）。
- 检索侧 query 向量化走 `_LlamaCppEmbeddingAdapter`，无需启动 Ollama。

### 本机踩坑时间线（避免重复绕路）

1. **误判「CPU 太慢」**：首次全量尝试很慢，一度以为 RTX 4050 没用上。
   看 `journalctl -u ollama` 发现 `discovering available GPUs...` 后只列出
   `cpu`、`total_vram="0 B"` —— Ollama 0.40.13（Arch 官方包）**没用上 GPU**，
   跑在 CPU。但 `vulkaninfo` 能看到卡，说明驱动没问题，是 Ollama 包本身的
   Vulkan/CUDA 后端在当前环境不可用（`OLLAMA_VULKAN=1` 无效，
   `OLLAMA_LLM_LIBRARY=vulkan` 反而让服务起不来）。

2. **真凶是 llamaIndex 逐条调用**：直接批量 `/api/embed` 60 条只要 **1.8s**，
   而走 llamaIndex `VectorStoreIndex(nodes)` 触发 embed 要 **55s**。
   修法：自己批量 embed（31ms/条），全量从「几小时」降到「~90s」。代码见
   `core/index.py` 的 `_batch_embed`。

3. **Ollama worker 会卡死**：即便单批很快，bge-m3 worker 处理若干请求后
   进入「CPU 占满 500%+ 但不返回」状态，`/api/embed` 直到 120s 超时。
   表现为 `urllib.TimeoutError`。旧代码里有自愈：`_embed_ollama` 超时后按
   `ollama.restart_cmd` 重启服务重试一次。但实测 worker 退化很快，自愈
   也常陷入「重启→又卡」循环。

4. **结论与对策**：Ollama 的 bge-m3 在本机**不可靠**；llama.cpp 纯 CPU 又慢；
   独显因风扇隐患不能上 GPU。最终改用**远程 embedding 服务（remote）**——
   本机零推理负担、稳定，代价是文本出网。Ollama 仅保留给 `ask_docs` 的
   **生成**模型（`qwen2.5:7b`）。

> 若你有健康的 GPU 或换到别的机器，把 backend 改回 `llamacpp` 并把
> `n_gpu_layers` 设 `-1` 即可本地加速；只是本机独显当前不可用。

## 8. 调参顺序建议

效果不理想时，按这个顺序查，别一上来换模型：

1. `search` 看命中的 `path` 对不对 → 不对就调 `inject_fields` / `threshold`；
2. 命中的路径对但片段被截断 → 调大 `short_doc_threshold` 或 `chunk_size`；
3. 片段对但答案编造 → 改 `query.system_prompt`，加大「只依据片段」的约束；
4. 中文召回差 → 换 embedding 模型（local 后端改 `embedding.local_model`），
   **记得删 data/ 重建**；
5. 综合多篇能力弱 → 加大 `top_k`，或把 `ask_docs` 换成 llamaIndex 的
   `query_engine`（response synthesis）。
